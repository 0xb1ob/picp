Behavior 17, last slice. The control scenarios start `bin/cp-view` on a scratch home with its clock pinned through
`tests/harness/process-clock.ts` and call its HTTP routes. A running operator session is the real
`startDashboardControl` server with pi's ports recorded. Start session runs fake `tmux` and `herdr` node scripts on a
PATH that holds only them, so the viewer's `execFile` argv, env and timeouts are real. `tests/e2e/operator-viewer.test.ts`
spawns the real `bin/cp-operator` with a fake `pi`, an optional fake `tailscale` and an `mktemp -d` pi agent dir.

The `*-ui` scenarios assert through the served tab in `tests/harness/dashboard.ts`. That tab is linkedom, not a real
browser: it fetches `/`, runs the served app script over a linkedom DOM, and its `fetch` reaches the same viewer over
real HTTP with a same-origin browser's headers. It has no layout engine and takes no screenshots, so no assertion here
is a pixel. The 390 px and 1440 px rules are pinned as the CSS `bin/cp-view` serves (P17-layout), each rule read in
its own `@media` context. The tab's `Date` moves only through `tab.shift(ms)`, which is how the 60 s Start and 90 s
Restart waits reach their `Failed` lines; the viewer's clock moves through `pin`. Each mapped row's note ends in
`covered-by:` cites of the asserting lines. `tests/viewer-control-retained.test.ts` keeps the client units no entry
point reaches; each `retained` row names its function.
